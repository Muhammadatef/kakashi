1 · Executive summary

Kakashi is an open-source, locally-executed privacy layer designed to prevent personal data, credentials, and sovereign identifiers from crossing the boundary between a user's device and any external Large Language Model. It installs as a first-class skill inside more than 20 agentic-AI platforms — Cursor, Claude Code, GitHub Copilot, OpenAI Codex, Windsurf, Cline, Continue, Aider, JetBrains Junie, Roo Code, and others — and exposes a loopback HTTP API that any additional Model-Context-Protocol (MCP) client can consult before shipping data.

Kakashi is not itself an artificial-intelligence system. It is a deterministic, rule-based safety layer that operates around AI systems. This design decision eliminates every class of AI-ethics concern that stems from opacity, hallucination, learned bias, or model drift, and yields four inherent properties that regulated agentic-AI deployments require:

  • Deterministic — the same input always produces the same masking output; no hallucinated tokens.
  • Auditable — every detection rule is a regular expression readable by a compliance officer.
  • Bias-free — no training data means no encoded bias; the same pattern fires for every user regardless of nationality, gender, or language.
  • Explainable — every finding carries its pattern identifier, its severity, and the specific article of the UAE Personal Data Protection Law that governs it.
The single strategic sentence. Kakashi is the sovereign privacy infrastructure that makes agentic AI safe to deploy at UAE national scale. Every module described in this document exists to reinforce that thesis.

2 · System architecture

Kakashi is composed of four horizontal layers. Every layer is independently testable and consumes only the layer directly beneath it, giving the system the shape below.

Fig 2.1 — Four-layer architecture. Each layer is a separate npm-package boundary and can be tested in isolation.

The layer boundaries are intentional. If an integration partner wants only the compliance reporter, they can import src/lib/pdpl-mapping.js and src/lib/reporter.js without adopting the CLI. If they want only database masking, src/engine/db/ is a stand-alone module. If a government pilot wants only the agent-guard daemon, it ships as a single-command binary. Modularity is a first-class value.

3 · Core engine — detection & masking

3.1 The pattern registry

Every detection lives in a single file, src/engine/patterns.js, as a plain JavaScript object with a stable schema:

{
  id:      'national_id',            // stable key -> token like [NATIONAL_ID_1]
  label:   'Emirates ID',            // English display name
  labelAr: 'الهوية الإماراتية',       // Arabic display name (for A4 i18n + HTML report)
  cat:     'id',                     // 'id' | 'pii' | 'cred'
  rx:      /\b784-\d{4}-\d{7}-\d\b/g, // regex
  validate: (m, text, i) => ...,      // optional false-positive filter
  fakeValues: ['784-1990-9999999-0']  // used by --mode fake
}

The id is stable across releases so a downstream user can rely on the token names (e.g. [NATIONAL_ID_1]) that appear in their masked files. The label and labelAr fields are free to evolve without breaking backwards compatibility. This separation is what allowed v1.1 to add Arabic labels to every existing pattern without breaking any existing masked artifact.

3.2 Checksum helpers

For the highest-stakes identifiers, Kakashi ships stand-alone checksum validators exported alongside the pattern registry:

  • luhnCheck(digits) — the ISO/IEC 7812-1 Luhn algorithm.
  • isValidEmiratesId(id) — 15-digit Luhn validation with mandatory 784 country prefix.
  • isValidIban(iban) — ISO 13616 mod-97 remainder validation for International Bank Account Numbers.

These validators are deliberately not wired into the pattern validate hooks. That decision reflects a threat-modelling principle: attackers frequently transpose digits, so a leaked identifier with a broken check digit is still a leaked identifier and must still be flagged. The stand-alone helpers are consumed by the reporter (§6) to badge findings as "checksum-verified" without discarding suspect-looking IDs.

3.3 The maskText algorithm

The masker is a single pure function with a five-step algorithm:

  1. Collect all regex matches from every active pattern.
  2. Sort matches by start position, then descending length (longer wins at the same position).
  3. Resolve overlaps by keeping the first match whose start is beyond the last accepted match's end (non-overlapping set).
  4. Assign consistent replacements — the same original value receives the same token throughout the document (alice@x.com always becomes [EMAIL_1]).
  5. Apply replacements end-to-start so earlier offsets remain valid as later text is rewritten.

3.4 Three masking modes

ModeExample outputWhen to use
typed (default)[EMAIL_1], [OPENAI_KEY_2]Preserves document readability and lets the AI reason about types
redact[REDACTED]Maximum anonymity when the AI does not need type context
fakeuser_a@example.comPreserves plausible LLM context for content-generation prompts

4 · File-format handlers

Kakashi supports over 50 file formats. The src/engine/formats/ directory contains a handler per family, each implementing two functions:

async function readFile(filePath)  -> { format, text, ...metadata }
async function writeMasked(inPath, outPath, data, replMap, maskedText)

The readFile extracts a canonical text representation for the masker; the writeMasked reconstructs the file in its original binary format after substitution. This is what lets Kakashi output a real Word file, not a text dump of one.

FormatLibraryStatusNotes
Text / code (40+ ext)native fsstableAny text-shaped file; format is trivially preserved.

PowerPoint (.pptx)jszipbest-effortXML <a:t> replacement.
PDF (.pdf)pdf-parsetext-onlyText extract → masked .md; real PDF round-trip tracked for v1.2.
JSON / JSONL / JSON5nativestableText-based; masking preserves structure.
YAML / TOML / XMLnativestableText-based; masking preserves structure.
CSV / TSVnativestableSame code path as text; delimiters preserved.

5 · Database masking layer

Kakashi v1.1 introduces client-side database masking. A user can point Kakashi at a live database, run a SQL (or NoSQL) query, and receive a masked local copy of the results without ever exposing the raw rows to any AI agent. Six drivers ship out of the box.

5.1 Driver registry

Drivers are lazily require()-d, so a user only installs the client library for the database they actually consume. If the client is missing, Kakashi throws a friendly error naming the exact npm install command.

5.2 CLI usage

# Count-only scan of a query — agent-safe, nothing written
kakashi db-scan "postgres://user:pass@host/db" -q "SELECT * FROM customers LIMIT 100"

# Mask a query result to a local JSONL file
kakashi db-mask "postgres://user:pass@host/db" \
  -q "SELECT * FROM customers WHERE country='UAE'" \
  -o masked_customers.jsonl -f jsonl

6 · PDPL compliance layer

The compliance layer, in src/lib/pdpl-mapping.js, links every detection pattern to specific articles of the UAE Federal Decree-Law No. 45 of 2021 concerning the Protection of Personal Data (PDPL). The mapping is the intellectual centrepiece of Kakashi's regulatory value proposition.

Design choice. The file is data, not logic. It has zero I/O and zero side-effects. Consumers (the reporter, the agent-guard API, any third-party dashboard) import the map and enrich their findings in-process. Keeping this layer declarative means a legal counsel or compliance officer can review it as one flat document without reading application code.

6.1 Article catalogue

Nine articles are formally mapped:

ArticleTitleKakashi coverage
Art. 1Definitions of Personal DataAll personal-info patterns
Art. 5Conditions for ProcessingConsent-preserving typed masking
Art. 6ConsentAvailable for future explicit-consent workflows
Art. 9Rights of the Data SubjectAvailable for right-to-erasure workflows
Art. 15Sensitive Personal DataEmirates ID, passport, IBAN, credit card, SSN
Art. 20Security of Personal DataEvery credential pattern (15+ classes)
Art. 21Reporting a Data BreachEvery leaked credential becomes a candidate breach event
Art. 22Cross-Border TransferEvery identifier destined for a foreign LLM
Art. 25Data Protection OfficerThe compliance report is DPO-ready

6.2 Severity heuristic

Every finding is scored:

  • critical — sensitive personal data (Art. 15) OR live credentials
  • high — personal data with strong re-identification risk (emails, phones)
  • medium — quasi-identifiers (names, dates of birth, IP)
  • low — weak identifiers (age, ambiguous dates)

6.3 Public API

const { enrich, summarize } = require('kakashi/src/lib/pdpl-mapping');

// enrich a single finding
enrich(finding) -> { ...finding, severity, articles, articleSummaries, checksumVerified }

// aggregate a whole scan
summarize(findings) -> { findings, summary: { total, byCategory, bySeverity, byArticle, topArticles } }

7 · Enterprise directory scanner

The scan-dir subcommand walks a directory tree, honours .gitignore and .kakashiignore, scans every supported file concurrently, and emits an aggregate compliance report in JSON, HTML, or Markdown.

7.1 Concurrency model

Rather than adopting worker_threads and paying the overhead of spawning worker processes and marshalling large buffers over MessageChannel, Kakashi v1.1 uses an async concurrency pool. Because file scanning is I/O-bound, a Promise-based pool of size N yields most of the wall-clock benefit of true parallelism without the operational cost. Worker-thread parallelism for CPU-bound XLSX/PDF workloads is tracked for v1.2.

7.2 Report rendering

The reporter at src/lib/reporter.js is a pure DATA-IN, STRING-OUT module with three renderers:

RendererConsumerNotes
renderJsonSIEM, CI, downstream toolsMachine-readable; every finding, every PDPL article, every timestamp.
renderMarkdownCLI stdout, GitHub PR commentsReadable at a glance; suitable for a pipeline comment bot.
renderHtmlAudit-ready deliverableBilingual EN / AR; dir="auto" for RTL; @media print ready for chrome --print-to-pdf.

7.3 CLI usage

kakashi scan-dir ./project \
  --format html \
  --lang ar \
  --parallel 8 \
  --output audit_report.html

# Then to convert to PDF (offline):
chromium --headless --print-to-pdf=audit.pdf audit_report.html

8 · Bilingual (EN / AR) i18n

Kakashi ships a native Arabic experience — not a Google-Translate afterthought. The src/lib/i18n.js module carries English and Arabic string tables, resolves the active language from four sources in priority order, and provides a t(key) helper with placeholder substitution:

  1. Explicit --lang CLI flag (highest priority)
  2. KAKASHI_LANG environment variable
  3. LANG environment variable if it starts with ar (e.g. ar_AE.UTF-8)
  4. Fallback: English

8.1 What is translated

  • All user-facing CLI strings — scan headers, finding summaries, error messages, success confirmations.
  • Every pattern label — label and labelAr are stored side-by-side in the pattern registry.
  • The full HTML compliance report — headers, table headings, PDPL article titles, severity labels, footer.
  • PDPL article titles in Arabic — title_ar alongside title_en in src/lib/pdpl-mapping.js.
  • A complete Arabic README at README.ar.md.

8.2 RTL preservation

Because Kakashi's replacement tokens (e.g. [NATIONAL_ID_1]) contain no bidirectional-embedding characters, the surrounding Arabic text preserves its natural right-to-left flow after masking. The HTML report declares dir="auto" so Arabic content renders RTL and English content LTR automatically within the same document.

9 · Agent-guard sidecar daemon

The agent-guard command in v1.1 is Kakashi's answer to the question that unlocks the "Agentic AI Solutions Developed in the UAE" category: how do you make agentic AI safe to deploy at national scale? The answer is to give every agent a local privacy sidecar it can consult before shipping any file to an external LLM.

9.1 Two roles

  1. Passive watcher. On startup, agent-guard subscribes to filesystem change events under a user-specified directory. Every changed file is scanned; every finding is recorded in a JSONL audit log with UTC timestamps. A Data Protection Officer can review the log at any time and see what sensitive data was present in the tree.
  2. Active HTTP API. agent-guard exposes three endpoints on 127.0.0.1 (loopback only — never a public interface). Any MCP-enabled agent, IDE plugin, or automation can call these synchronously before shipping data.

9.2 HTTP endpoints

Verb + PathBodyResponse
GET /health—{ ok, watching, uptimeMs, filesScanned, totalFindings, version }
POST /scan{ "path": "..." }{ path, summary } — PDPL-enriched summary; no raw values
POST /mask{ "path": "...", "output": "..." }{ output, replacements }

9.3 Loopback enforcement

Belt-and-braces security. Even though the daemon binds to 127.0.0.1, every incoming request is additionally checked against req.socket.remoteAddress and rejected with 403 unless the origin matches a loopback prefix (127., ::1, ::ffff:127.). This defends against edge cases where a reverse proxy or Docker network setup might have forwarded a non-local request to the daemon.

Zero-network-call preservation. agent-guard never opens an outbound socket. All state is in-memory plus one local JSONL log. Kakashi's "nothing leaves your machine" guarantee holds even while running as a long-lived daemon.

11 · Trust boundary & threat model

Fig 11.1 — The Kakashi trust boundary. Only masked artifacts and summary counts cross it.

11.1 Four defence-in-depth defaults

  1. scan prints counts only; verbose per-finding previews require an explicit --verbose.
  2. mask writes to disk; it never streams the masked bytes to stdout in the default flow.
  3. audit is documented as deliberately verbose and is only invoked explicitly by the operator.
  4. agent-guard's /scan API returns the PDPL summary — never the raw finding values, even over loopback.

11.2 STRIDE threat model

CategoryThreatMitigation
SpoofingNon-loopback caller impersonates a local agentLoopback bind + remoteAddress hard-check
TamperingMalicious patch disables a detection ruleSigned npm publisher, MIT-licensed source auditable line-by-line
RepudiationUser denies having exposed a credentialJSONL audit log + compliance report with UTC timestamps
Information DisclosureKakashi leaks the secrets it detectsCounts-only default; no telemetry; no error reporting
DoSEnormous input file exhausts memoryStreaming per-row for DB, per-file try/catch for scan-dir, --limit
Elevation of PrivilegeDaemon reads files outside its watched dirOnly reads paths the caller asks for; respects OS permissions

12.1 CI integration

- name: Kakashi privacy scan
  run: |
    npm install -g @muhammadatef/kakashi
    kakashi scan-dir . -f json -o kakashi-report.json
- name: Upload compliance report
  if: always()
  uses: actions/upload-artifact@v4
  with: { name: kakashi-report, path: kakashi-report.json }

Because kakashi scan-dir exits 1 when findings are present, the pipeline can be configured to fail pull requests that leak new sensitive data — turning Kakashi into a pre-merge safety gate.
